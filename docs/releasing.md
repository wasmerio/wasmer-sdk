# Releasing the Wasmer SDK

The repository has two workflows. `ci.yml` validates the Rust SDK and UniFFI first, then runs the JavaScript and Python suites in parallel. It also checks the `wasmer-sdk` source package without pretending that the current registry-normalized crate is usable. `release.yml` is triggered by a `v<version>` tag, builds and tests `wasmer-sdk` and `wasmer-sdk-uniffi`, then publishes npm and Python packages in parallel. This ordering makes the Rust API and native facade the release gate while keeping the platform packaging work independent.

All four public package manifests deliberately carry the same version. Before creating a tag, update `rust/Cargo.toml`, `rust/uniffi/Cargo.toml`, `js/package.json`, `js/package-lock.json`, and `python/pyproject.toml`, then run `python3 .github/scripts/check-release-version.py`. The tag must match exactly: version `8.0.0-alpha.1` is released by tag `v8.0.0-alpha.1`. The first workflow attempt checks every target registry before the first upload; reruns skip artifacts that the same release already published. Registry versions are immutable, `@wasmer/sdk@0.1.0` already exists, and the established Rust crate is on the 7.x line, so the manifests must be moved together to a new unused version before the first release from this repository.

The workspace resolves the Wasmer crates from the `sdk` branch of `wasmerio/wasmer`. `Cargo.lock` pins the exact Git commit used by CI; moving the branch does not silently change a locked build. Update the pin intentionally with `cargo update` when adopting a newer `sdk` commit.

crates.io deliberately removes workspace patch overrides from published packages. The current SDK uses runtime-hook APIs that are present on Wasmer's `sdk` branch but absent from the released `wasmer-wasix` crate, so publishing the Rust crates with `--no-verify` would create a broken release. The crates.io steps are therefore commented out for now. Once that Wasmer release exists, update the exact dependency versions, remove the Git patches, restore the two publication steps, and add crates.io back to the registry preflight. npm and Python artifacts embed the Git-pinned runtime and can be published after the native build gate succeeds.

The `npm` environment should be registered as the trusted publisher for `@wasmer/sdk`, using repository `wasmerio/wasmer-sdk` and workflow filename `release.yml`. The `pypi` environment should likewise be registered as the PyPI trusted publisher for `wasmer-sdk`, also using `release.yml`. Both publication jobs request `id-token: write`, so npm and PyPI exchange GitHub's short-lived OIDC identity for publication credentials; no long-lived npm or PyPI token is stored in the repository.

Python releases contain one `py3-none-<platform>` wheel per supported runner architecture. This is intentional: UniFFI loads a native library through `ctypes`, so the artifact is platform-specific but independent of the CPython extension ABI and can be shared by all supported Python 3 versions on that platform.

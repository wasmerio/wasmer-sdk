# Sandbox latency results — 2026-09-01

## Outcome

With artifacts cached and measurements run sequentially, native Wasmer is the
fastest path at every layer tested. Its largest practical advantage is not only
sandbox construction; the entire new-sandbox-to-completed-CPython-command path
has a p50 of **25.05 ms** and p95 of **25.45 ms**.

The most important architectural finding is that sandbox creation and readiness
to execute are not equivalent for the remote providers. Modal's standard
`Sandbox.create()` has a 335.65 ms median, but a new sandbox's first completed
Python command takes 1,611.38 ms end to end. Modal V2 improves this to 1,228.54
ms, while E2B takes 807.41 ms. The first-exec penalty must remain a first-class
metric; reporting creation alone would be misleading.

## Method

Each group contains 30 sequential samples. p95 uses linear interpolation over
the raw samples. Preparation was untimed:

- Wasmer packages and compiled artifacts were already present in `.wasmer`.
- Docker images were pulled before sampling.
- Modal registry images were resolved before sampling.
- The E2B multi-runtime template was built before sampling.

The conditions mean:

- **new sandbox/container:** a new isolation boundary with artifacts cached;
- **existing sandbox/container:** a command through a running isolation boundary;
- **application startup:** a new runtime process in an existing sandbox, so the
  measurement includes command transport and process startup but not sandbox
  creation;
- **end to end:** new sandbox, CPython startup, no-op command, and completion.

This is the useful definition of cold versus warm for the requested scenario:
"cold" is a newly allocated sandbox, while "warm" reuses an existing sandbox.
An empty registry/image cache is an artifact-acquisition benchmark and was
intentionally excluded.

The APIs map cleanly to these phases: Modal exposes `Sandbox.create()` and
`Sandbox.exec()` separately, and E2B exposes `Sandbox.create()` and
`commands.run()` separately. Modal's V2 backend is reported separately because
it is beta and is documented as a lower-time-to-interactive backend.

## Sandbox creation: new isolation boundary

Artifacts are warm; every measured sandbox/container is new.

| Provider | p50 | p95 |
|---|---:|---:|
| Wasmer SDK | **0.140 ms** | **0.161 ms** |
| Docker CLI | 205.952 ms | 218.626 ms |
| Modal V2 (`us-west`) | 319.186 ms | 337.165 ms |
| Modal standard (`us-west`) | 335.645 ms | 441.207 ms |
| E2B custom template | 517.160 ms | 1,567.845 ms |

Wasmer's median is about 1,471× lower than Docker, 2,280× lower than Modal V2,
2,398× lower than standard Modal, and 3,694× lower than E2B. These ratios compare
a local in-process runtime with a local daemon and remote services; they describe
observed latency, not provider compute performance in isolation.

## Warm per-command latency

This runs a minimal successful command in an existing sandbox/container.

| Provider | p50 | p95 |
|---|---:|---:|
| Wasmer SDK | **5.569 ms** | **5.910 ms** |
| Docker CLI | 49.011 ms | 55.136 ms |
| E2B | 82.831 ms | 104.161 ms |
| Modal standard | 103.326 ms | 130.142 ms |
| Modal V2 | 104.100 ms | 237.514 ms |

This is the best estimate of each command path's floor. Docker includes CLI to
daemon transport and process creation. Modal and E2B include the real client to
remote-sandbox round trip. The remote medians should therefore be interpreted
with the client region, provider region, and current network path attached.

## End-to-end Python no-op

This is the latency users see for: create a new sandbox, start CPython, run
`pass`, and receive completion.

| Provider | p50 | p95 |
|---|---:|---:|
| Wasmer SDK | **25.049 ms** | **25.449 ms** |
| Docker CLI | 281.121 ms | 316.973 ms |
| E2B | 807.411 ms | 900.636 ms |
| Modal V2 | 1,228.539 ms | 1,578.785 ms |
| Modal standard | 1,611.380 ms | 2,340.079 ms |

The observed end-to-end median minus the separately measured creation and warm
Python-startup medians is:

| Provider | Additional first-exec cost |
|---|---:|
| Wasmer SDK | approximately 0 ms |
| Docker CLI | 19.719 ms |
| E2B | 205.401 ms |
| Modal V2 | 800.549 ms |
| Modal standard | 1,161.902 ms |

This residual is not arithmetic noise for the remote services: the application
startup suite uses an already-executing sandbox, while end to end executes the
first command in each new sandbox. It exposes the cold-to-interactive work that
`create()` alone does not capture.

## Conclusions and next measurements

1. **Keep creation, first exec, runtime startup, and warm commands as four
   metrics.** The Modal and E2B results prove they cannot be collapsed safely.
2. **Treat Wasmer's compiled-package cache as preparation.** With it populated,
   sandbox construction is effectively free compared with runtime startup.
3. **Optimize persistent workloads differently from one-shot workloads.** A
   persistent interpreter could avoid Wasmer's roughly 19 ms CPython process
   startup above the 5.6 ms command floor.
5. **Run a region matrix next.** Repeat the remote suites from matched `us-west`,
   `us-east`, and EU clients, recording RTT and provider placement. E2B needs an
   exposed or documented region selector for a controlled regional comparison.
6. **Add concurrency separately.** These runs measure sequential latency, not
   allocation throughput or contention at 10–100 concurrent sandbox creates.
7. **Measure artifact acquisition separately.** A fresh `.wasmer` cache and fresh
   Docker/remote images answer a packaging/distribution question, not sandbox
   startup.
